## 10. Письма пользователям (20.11.2026)

## 11. Несколько вещей на одном фото (19.11.2026)

- `/api/ai/recognize-multi`: тот же порядок, что у других маршрутов ИИ: zod-проверка формы (JPEG до 2 МБ), `guardAiRequest("recognize")` (сессия, активный аккаунт, квота списывается до Gemini), категории для промпта сервер берёт из базы. `category_id` из ответа сверяется со списком пользователя, строки и теги обрезаются до лимитов БД, рамки приводятся к 0–1000, число предметов ≤ 30. В режиме `en` русские поля обнуляются. В логи — только тип ошибки и статус.
- `createItemsBatch`: до 30 вещей; id — uuid без повторов; путь каждой вырезки строго `{свой user_id}/{этот item_id}/{uuid}.jpg`, общий снимок — в папке первой вещи, все пути разные; иначе `photoInvalid` и удаление загруженного. Поля проходят ту же `itemFieldsSchema(mode)`/`toItemRow`, что и обычная вещь. Пути копий генерирует сервер. Копирование идёт сессией пользователя, поэтому Storage RLS действует: проверено, что копия своего файла в чужую папку отклоняется. Ошибка на любом шаге удаляет вставленные вещи и все загруженные и скопированные файлы парами.
- Проверено под тестовым аккаунтом (фото щита, 12 предметов, сохранено 10): у каждой вещи 2 фото, ровно одно главное, 4 файла только в своей папке; после удаления вещей файлы удалены (40 из 40).

## 12. Отозванная сессия и выход (19.11.2026)

- Найдено на Preview: после выхода на другом устройстве (`signOut` по умолчанию global) страница уходила в цикл `/` ↔ `/login` (`ERR_TOO_MANY_REDIRECTS`): proxy принимал токен по подписи, `getUser` его отклонял. Воспроизведено локально (сессии отозваны отдельным клиентом).
- Исправление: `requireUser()` → `/auth/signout` (удаляет cookie сессии этого устройства, затем `/login`); «Выйти» с `scope: "local"`. Проверено: с отозванной сессией открывается экран входа; выход в браузере не завершает сессию на другом устройстве.
- `/auth/signout` — GET без проверки происхождения: чужая ссылка может разлогинить пользователя на этом устройстве (logout CSRF). Данные не раскрываются и не меняются; принятый риск.

## 13. Защита от дублей (19.11.2026)

- Миграция `20261120010000_duplicate_check` безопасна для v1.1.0: новая nullable-колонка `item_photos.source_hash`, индекс `(user_id, source_hash)`, новая функция `similar_items` (SECURITY INVOKER, `search_path = ''`, execute только `authenticated`). Права на таблицу прежние (новая колонка под теми же политиками RLS).

## Принятые риски

1. **Отметку keepalive можно подделать.** Любой, у кого есть публичный anon key (он есть в коде страницы), может вызвать `keepalive()` и обновить время «Последняя проверка базы». Данные при этом не раскрываются и не меняются. Принято сознательно (этап 7).
2. **CSP ограниченная.** Включены `frame-ancestors`, `base-uri`, `object-src`; полный CSP со `script-src` не включён: Next.js вставляет inline-скрипты, а строгая политика с nonce потребовала бы отключить статическую отдачу страниц. React экранирует вывод, `dangerouslySetInnerHTML` в коде не используется.
3. **Отметку онбординга пользователь может изменить** (`user_metadata`): это повлияет только на повторный показ подсказок.
4. **Письмо о регистрации приходит только при регистрации через приложение.** Регистрация напрямую через API Supabase письма не даёт; такой аккаунт всё равно `pending`, ничего не может и виден в `/admin` со счётчиком.
5. **Роль админа назначается SQL-командой**, интерфейса для этого нет (сознательно).
6. **Карта исходников service worker** (`/serwist/sw.js.map`) доступна публично: в ней только код worker'а, секретов нет.
