# Inventory: приложение для инвентаризации вещей

Мобильно-ориентированное веб-приложение (PWA) для учёта личных вещей. Много независимых пользователей: каждый регистрируется по email и паролю и видит только свои данные. Интерфейс на двух языках (RU/EN). Gemini API распознаёт вещи по фото, понимает голосовые команды («положи на верхнюю полку в шкафу в спальне на даче») и отвечает на голосовые вопросы («где моя дрель?»).

## Главные сценарии первой версии

1. **Добавить вещь:** фото с камеры → Gemini предлагает название RU/EN, категорию, описание → пользователь голосом или текстом говорит, куда положил → приложение находит место в дереве (или предлагает создать недостающее) → пользователь подтверждает и сохраняет.
2. **Режим «я сейчас здесь»:** пользователь один раз выбирает текущее место (например «Дача → Гараж → Стеллаж»), и все новые вещи по умолчанию кладутся туда. Место видно в шапке, его можно сменить или сбросить. Хранится на устройстве (localStorage) **отдельно для каждого пользователя**: ключ `inventory.currentLocationId.<user_id>` (старый общий ключ переносится в аккаунт, которому принадлежит место). Автоматически не стирается: если места нет в списке, `useCurrentLocation` один раз делает `router.refresh()`; сбрасывает пользователь или удаление этого места. Менять только через `useSetCurrentLocation()`. **Место новой вещи и есть «Я здесь»** (`useHerePlace()` в форме добавления и в «Нескольких вещах»): выбор там списком, голосом или крестиком меняет «Я здесь» везде. Правка места существующей вещи и «Переместить» его не трогают. Список «Вещи» без места в адресе открывается на «Я здесь» (с вложенными): клиент делает `router.replace(?location=<id>)`; явный выбор держится в адресе (`location=<uuid>` или `location=all`), «Сбросить» = все места. **Фильтр места в «Вещах» и есть «Я здесь»:** выбор места в фильтре или ссылка `/?location=<id>` ставит его, «Все места» и «Сбросить» сбрасывают; смена «Я здесь» в шапке сразу перестраивает список (синхронизация только после гидратации). Не меняют «Я здесь» только выборы места для конкретной вещи или места: «Переместить», «Где находится» при создании места, перенос места.
3. **Найти вещь голосом или текстом:** «где моя дрель?» → список найденных вещей с фото и полным путём места.
4. **Просмотр:** фильтр по месту (включая все вложенные) и категории, вид «галерея» или «таблица».

Не делаем в первой версии: количество и расходники, типы мест с иконками, отдельная логика для переносимых коробок, общий доступ между пользователями.

## Стек (не менять без согласования)

- **Next.js** (актуальная стабильная версия, App Router) + **TypeScript** (strict) + **Tailwind CSS**
- **Supabase**: Postgres, Auth (email + пароль), Storage (фото)
  - клиент: `@supabase/supabase-js` + `@supabase/ssr` (сессия в cookies, middleware обновляет сессию)
  - миграции: Supabase CLI, файлы в `supabase/migrations/`

- **i18n**: `next-intl`, словари `messages/ru.json` и `messages/en.json`, язык интерфейса по умолчанию `en` (не по браузеру; русский включается переключателем и запоминается в cookie)
- **PWA**: web manifest + service worker (Serwist), иконки 192/512 и maskable
- **Хостинг**: Vercel
- Валидация `zod`, формы `react-hook-form`, иконки `lucide-react`

```
AI_DAILY_LIMIT_PER_USER=100     # запасной дневной лимит ИИ, если у тарифа plans.ai_daily_limit пуст
GOOGLE_BOOKS_API_KEY=           # только сервер, необязательно; без него Google Books часто отвечает 429
CRON_SECRET=                    # только сервер; Vercel Cron шлёт его в Authorization: Bearer …
SUPABASE_SERVICE_ROLE_KEY=      # только сервер, только для удаления пользователя админом
RESEND_API_KEY=                 # только сервер; письма админу (необязательно)
ADMIN_NOTIFY_EMAIL=             # куда слать письма админу
MAIL_FROM=                      # "Inventory <noreply@домен>", домен подтверждён в Resend; без него письма пользователям не уходят
```

**Keepalive:** Vercel Cron (`vercel.json`, раз в сутки в 06:00 UTC) вызывает `/api/cron/keepalive`. Маршрут без `Authorization: Bearer $CRON_SECRET` отвечает 401, иначе вызывает RPC `keepalive()`: она записывает `now()` в однострочную таблицу `system_status.last_keepalive_at` и возвращает его (SECURITY DEFINER, доступна `anon`; что её может вызвать любой с anon key и сдвинуть время — принятый риск). В Настройках показывается «Последняя проверка базы» (логи Vercel Hobby живут час). Нужно, чтобы проект Supabase Free не уходил в паузу после 7 дней без запросов.

Ключи никогда не попадают в клиентский код, в git и в логи. `.env.local` в `.gitignore`, `.env.example` держим актуальным. Service role key Supabase используем **только** в `lib/supabase/admin.ts` (`server-only`) и только в админском действии «Удалить пользователя», после проверки `admin_check_delete()` сессией админа. Всё остальное работает через сессию пользователя и RLS.

## Одобрение аккаунтов и админ

- **`profiles`**: `user_id, status ('pending' | 'active' | 'disabled'), role ('user' | 'admin'), created_at, status_changed_at`. Новая регистрация получает `pending` (триггер на `auth.users`). Пользователь может только читать свою строку; прав на запись нет ни у кого, кроме админских функций. Статус хранится в таблице, а не в JWT: изменение действует сразу.
- **Блокировка в базе:** все политики RLS (таблицы и Storage) содержат `(select public.is_active())`; `consume_ai_quota_v2` у неактивного аккаунта падает с 42501, маршруты ИИ отвечают 403 `accountInactive`. Новые таблицы и политики делаем так же. В интерфейсе layout `(app)` показывает неактивным только экран «ожидает одобрения» / «отключён» и «Выйти».
- **Админ** (`role = 'admin'`, назначается SQL-командой, не через приложение). Три экрана, все через `requireAdmin()` (остальным страница 404):
  - `/admin` — две карточки: «Пользователи» (число и красный счётчик ожидающих, `admin_overview()`) и «Тарифы» (число);
  - `/admin/users` — `admin_list_users_v3(search, status, plan, sort, limit, offset)`: поиск по части email (`%`/`_` экранируются), фильтры статуса и действующего тарифа, сортировка (`new`/`old`/`email`/`items`/`ai`/`seen`, ожидающие всегда сверху), страницы по 50 с `total`. Всё в адресе (`lib/admin/filters.ts`), смена фильтров и страниц — `router.replace` (без новых записей истории). Компактная строка (email, статус, тариф, вещи; на широком экране ещё ИИ и дата) раскрывается в карточку: даты, цифры, ручной тариф, «Активировать», «Отключить», «Удалить»;
  - `/admin/plans` — названия RU/EN, лимиты, порядок стрелками (`admin_reorder_plans(codes[])`, весь порядок одним вызовом), «На тарифе N» (`admin_plan_stats()`: `users_now` — действующий тариф, `users_linked` — ручной или подписка, даже истёкшие), «Добавить тариф» (`admin_create_plan`, код `^[a-z0-9_]{1,32}$` навсегда, встаёт в конец), «Удалить» (`admin_delete_plan`: не `free` и только без связанных пользователей, ошибка `P0011`; внешние ключи `profiles` тоже не дадут).
  Функции `admin_list_users_v3`, `admin_overview`, `admin_plan_stats`, `admin_pending_count`, `admin_set_status`, `admin_check_delete`, `admin_set_plan`, `admin_update_plan`, `admin_create_plan`, `admin_delete_plan`, `admin_reorder_plans` (SECURITY DEFINER) сами проверяют `is_admin()`, не трогают себя и других админов и **не возвращают вещи, места и фото**. `admin_list_users_v2` больше не используется (оставлена в базе для отката). Счётчик ожидающих — на иконке «Настройки» и на ссылке «Админ». Письмо о новой регистрации ведёт на `/admin/users?status=pending`.
- **Письма** (Resend, `lib/notify/`, всегда в `after()`, ошибка почты не мешает действию, только простой текст):
  - админу (`admin-email.ts`): о новой регистрации (`signUp`) и об удалении аккаунта самим пользователем;
  - пользователю (`user-email.ts`): «регистрация получена», «аккаунт одобрен», «доступ восстановлен», «доступ закрыт» — только при реальной смене статуса (`admin_set_status` возвращает прежний статус, email и `data_lang`). Язык письма: `en` → английский, иначе русский. **Отправляются, только если задан `MAIL_FROM`** с доменом, подтверждённым в Resend (тестовый отправитель Resend доставляет только владельцу аккаунта).
- Общее для писем: ссылка в письме строится из `VERCEL_PROJECT_PRODUCTION_URL`, а не из заголовков запроса. Регистрация в обход приложения (прямо через API Supabase) письма не даёт — принятый риск: такой аккаунт всё равно `pending` и виден в `/admin`.

## Тарифы

- **`plans`**: `code` (ключ), `name_ru`, `name_en`, `item_limit` (null = без лимита), `ai_daily_limit` (null = запасной `AI_DAILY_LIMIT_PER_USER`), `sort_order`, `stripe_price_month`, `stripe_price_year` (nullable, для будущей оплаты). Стартовые: free 200/20, plus 500/100, pro 1000/300, unlimited ∞/1000. Читают активные пользователи, пишут только админские функции (`/admin/plans`, действует сразу).
- **`profiles`**: два независимых набора полей, подписка никогда не перезаписывает решение админа:
  - ручной тариф: `manual_plan` (null = не назначен), `manual_until` (null = бессрочно) — назначает админ в `/admin/users` (`admin_set_plan(user, code, until)`);
  - подписка (заполнит webhook Stripe): `subscription_plan`, `subscription_status`, `subscription_period_end`, `stripe_customer_id`, `stripe_subscription_id`.
  Пользователь эти колонки менять не может (колоночный grant только на `data_lang`).
- **Действующий тариф** считает только `effective_plan(user)` (SECURITY DEFINER, пользователям недоступна): ручной, если назначен и срок не вышел → иначе подписка при `active`/`trialing`/`past_due` и `subscription_period_end > now()` → иначе `free`; возвращает код, источник (`manual` | `subscription` | `default`) и дату окончания. Окончание срока или подписки возвращает на free без фоновых задач; данные не удаляются. Наружу: `my_plan()` (свой тариф, число вещей, запросы ИИ за 24 ч), `admin_list_users_v3()`, `admin_plan_stats()`.
- **Лимит вещей**: приложение проверяет до сохранения (`getMyPlan()` в `lib/plans.ts`, ошибка `planLimit`), «Несколько вещей» сохраняет сколько помещается и сообщает, сколько не поместилось (файлы остальных удаляются). В базе — триггер `items_enforce_plan_limit` (BEFORE INSERT, блокировка на пользователя, видит строки той же пачки; код ошибки `P0010` → `planLimit`), обойти через API нельзя. Админы без лимитов. Понижение лимита ничего не удаляет.
- **ИИ по тарифу**: `consume_ai_quota_v2` → `ok` | `limit` (дневной лимит тарифа) | `items_limit` (вещей ≥ лимита: **весь ИИ отключён**, включая фоновый и пакетный перевод; квота не списывается). Маршруты отвечают 403 `itemsLimit`. Клиент: `PlanProvider` в layout, `useAiOff()` отключает кнопки ИИ и добавление вещей, `PlanLimitBanner` и подсказка `usePlanLimitText()`. Работают просмотр, правка, обычный поиск, удаление. Админ: без лимитов, запросы только записываются.
- Настройки: «Тариф: Free · 45 из 200 вещей», полоса, «ИИ: 7 из 20 запросов за 24 часа», предупреждение с 90 %, сообщение при лимите.

### Подключение Stripe (будущая задача, сейчас не сделано)

1. Ключи только на сервере: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`; в `plans` заполнить `stripe_price_month` / `stripe_price_year` (id цен из Stripe).
2. **Оформление**: server action создаёт Checkout Session (`mode: subscription`, `price` из тарифа, `client_reference_id = user_id`, `customer` = `stripe_customer_id`, если уже есть), редирект на Stripe. Управление/отмена — ссылка на Customer Portal (`billing_portal.sessions.create`).
3. **Webhook** `app/api/stripe/webhook/route.ts`: тело читать как raw text, проверить подпись (`stripe.webhooks.constructEvent`), ответить 400 при ошибке. Только здесь service role (`lib/supabase/admin.ts`), как в удалении пользователя. Маршрут открыть в `proxy.ts` (без сессии).
4. **События**:
   - `checkout.session.completed` → записать `stripe_customer_id` (и `stripe_subscription_id`) пользователю из `client_reference_id`;
   - `customer.subscription.created` / `.updated` / `.deleted` → найти пользователя по `stripe_customer_id`, записать `subscription_plan` (по `items.data[0].price.id` → `plans.stripe_price_*`), `subscription_status` (`status` как есть), `subscription_period_end` (`current_period_end`), `stripe_subscription_id`; при `.deleted` — статус `canceled`;
   - `invoice.payment_failed` / `invoice.paid` — только для уведомлений (статус придёт в `subscription.updated`).
5. **Правила**: webhook пишет **только поля подписки**, никогда `manual_*` (ручной тариф имеет приоритет сам по себе в `effective_plan`). Идемпотентность: таблица `stripe_events (id text primary key, received_at)` без доступа для пользователей; уже обработанный `event.id` пропускать. Порядок событий не гарантирован: брать данные подписки из события (или `stripe.subscriptions.retrieve`), а не вычислять приращения.
6. Миграция для этого: только новая таблица `stripe_events` (безопасная). Проверки: подпись, повтор события, ручной тариф не перезаписан, отмена → free после `period_end`.

## Языки записей

`profiles.data_lang`: `'en'` (только английский), `'ru'` (на экране русский, английский заполняется сам в фоне), `'ru_en'` (оба языка, как было). При регистрации: русский интерфейс → `ru`, иначе `en` (передаётся в `signUp` метаданными, читается триггером один раз). Существующие аккаунты — `ru_en`. Пользователь меняет **только эту колонку** своего профиля (колоночный grant + политика).

- Логика в `lib/data-lang.ts`: язык показа (`displayLang`: en/ru фиксированы, ru_en — по интерфейсу, с подстановкой второго языка), поля форм (`editLangs`), обязательное название (`hasRequiredName`), запись в базу (`resolvePair`): скрытый язык при правке **не трогается**; в `ru` при изменении русского текста устаревший английский очищается и переводится заново; в `ru_en` пустое английское название получает русский текст, пустое русское остаётся пустым.
- Server actions сами читают режим (`getDataLang()`), клиенту не доверяют. Клиент получает режим из `DataLangProvider` в layout (`useDataLang()`), там же живёт пакетный перевод с прогрессом (`TranslationProgress`), поэтому он не прерывается при переходах.
- Переключение мгновенное, ничего не удаляется. Если в показываемых языках есть записи без текста (`promptLangs`), Настройки предлагают «Перевести N записей сейчас?»; при отказе у записи есть кнопка «Перевести», а в Настройках строка «Без перевода: N».
- Теги без отметки языка: в `en` скрыты кириллические, в `ru` — только латинские (`isVisibleTag`); скрытые теги сервер сохраняет при правке.

## Модель данных

У всех таблиц есть `user_id uuid not null default auth.uid() references auth.users on delete cascade` и включён RLS с политиками `user_id = (select auth.uid())` на select/insert/update/delete (исключение: `ai_usage`, см. ниже). Права выдаём явно: `anon` ничего, `authenticated` только нужное.

**Связи между таблицами только по паре `(id, user_id)`.** Postgres проверяет внешние ключи в обход RLS, поэтому ключ только по `id` позволил бы сослаться на чужое место, категорию или вещь, зная uuid. У каждой родительской таблицы есть `unique (id, user_id)`, а внешние ключи составные: `(parent_id, user_id)`, `(location_id, user_id)`, `(category_id, user_id)` (с `on delete set null (category_id)`, чтобы `user_id` не обнулялся), `(item_id, user_id)`. Новые связи делаем так же.

**Ограничения длины** (check в БД, те же правила в zod):
- названия мест и вещей: `name_ru` и `name_en` nullable, но хотя бы одно задано (check `*_name_present`); каждое 1–200 символов после trim. Какое обязательно, решает режим языков записей (см. ниже);
- названия категорий: то же, 1–100 символов;
- описания: до 2000 символов, nullable;
- теги: не больше 50.

- **`locations`**: дерево мест любой глубины (parent-child).
  `id, user_id, parent_id (nullable, ссылка на locations.id, on delete restrict), name_ru, name_en, sort_order, created_at`.
  Место без родителя это верхний уровень (дом, дача). Перенос шкафа в другую комнату = смена `parent_id`; вещи внутри переезжают вместе с ним. Запрещаем циклы (нельзя сделать место потомком самого себя), проверка в триггере.
  SQL-функции:
  - `location_descendants(loc_id)`: id места и всех потомков (recursive CTE), для фильтра «всё на Даче».
  - представление `location_paths` (`security_invoker`): `id, user_id, parent_id, depth, path_ru, path_en, id_path` — полный путь на обоих языках («Дача → Гараж → Стеллаж»).
  - представление `location_item_counts` (`security_invoker`): `location_id, direct_items, total_items` — вещей прямо в месте и всего, включая вложенные.
- **`categories`**: `id, user_id, name_ru, name_en, sort_order, created_at`. При регистрации триггер на `auth.users` создаёт стандартный набор: Мебель, Инструменты, Кухня, Электроника, Одежда, Документы, Хозтовары, Спорт и отдых, Личные вещи, Другое (в режиме `en` только английские названия, иначе на обоих языках). Пользователь может переименовывать, добавлять и удалять свои категории; при удалении у вещей `category_id` становится null.
- **`items`**: `id, user_id, location_id (nullable, on delete restrict), category_id (nullable, on delete set null), name_ru, name_en, description_ru, description_en, tags text[], book_author, book_year, book_isbn, created_at, updated_at`.
  Поля книги (v1.8.0, nullable, одно значение без RU/EN, одинаковые во всех режимах языков): `book_author` (1–300), `book_year` (1400–2100), `book_isbn` (только цифры ISBN-10/13, X в конце ISBN-10; контрольную сумму проверяет приложение, `lib/books/isbn.ts`). В zod поля необязательные: кто их не прислал, не трогает сохранённые.
  Поиск: генерируемая колонка `search_text_v2` (имена, описания и теги на обоих языках + автор и ISBN), нормализованная функцией `normalize_search()`: нижний регистр и **`ё` → `е`**. Поисковые слова в приложении нормализуем так же. Расширение `pg_trgm` (схема `extensions`) и GIN-индекс. Старая `search_text` (без автора и ISBN) и `search_items` остались для отката на 1.7.0; убрать их можно отдельной отложенной миграцией.
- **`item_photos`**: `id, item_id (on delete cascade), user_id, storage_path, is_primary, created_at`. Не больше одного `is_primary` на вещь; `storage_path` строго `{user_id}/{item_id}/….jpg`. Файлы в Storage при удалении вещи сами не удаляются: это делает приложение.
- **`ai_usage`**: `id, user_id, kind ('recognize' | 'voice_place' | 'search' | 'translate' | 'transcribe' | 'categorize'), created_at`. Для дневного лимита запросов к Gemini: **общий лимит на все виды, скользящие 24 часа**. Проверка и запись атомарно через RPC `consume_ai_quota_v2(p_kind, p_fallback)` (блокировка на пользователя): лимит берётся из тарифа (см. «Тарифы»), квота списывается до вызова Gemini. **Политики только select и insert** (без update/delete): anon key есть в браузере, и с правом delete пользователь мог бы стереть свои записи и обойти лимит.

Storage: приватный бакет `item-photos` (только `image/jpeg`, до 5 МБ), путь `{user_id}/{item_id}/{uuid}.jpg`, политики пускают только в папку своего `user_id`. Фото показываем через signed URLs.

## Работа с Gemini

- Все вызовы в `lib/ai/` и в маршрутах `app/api/ai/*`. Каждый маршрут: валидирует вход через `zod`, затем `guardAiRequest(kind)` из `lib/ai/route.ts` (сессия + `consume_ai_quota_v2`: тариф, лимит вещей, дневной лимит), затем `generateJson()` из `lib/ai/gemini.ts` (схема для Gemini строится из той же zod-схемы, что проверяет ответ). В логи пишем только тип ошибки и статус, без текста запроса.
- Задержки Gemini под нагрузкой сильно скачут: `generateJson()` делает короткие попытки (10 с + 15 с) с повтором при таймауте и 500/503. Для простых задач передаём `thinking: "low"`; если модель не поддерживает этот параметр, запрос повторяется без него.
- **Перевод названий** (`/api/ai/translate`): `{ text, from: 'ru' | 'en', kind?: 'name' | 'description' }` → `{ text }` (название до 200, описание до 2000 символов). Только в режиме `ru_en`, кнопка «Перевести» в форме активна, когда заполнено одно поле.
- **Пакетный перевод записей** (`/api/ai/translate-batch`, `lib/translate/records.ts`): сервер сам берёт из базы следующую пачку записей без нужного языка (до 40 записей и ~8000 символов) → один запрос к Gemini = 1 единица лимита → пишет **только пустые поля** (`update … where поле is null`). Без работы квота не тратится. Те же функции: кнопка «Перевести» у записи (`targets`), фоновый перевод после сохранения в режиме `ru` (`translateAfterSave`, `after()`), тихое догоняние в режиме `ru` при открытии приложения.
- **Режим языков в ИИ:** маршруты сами читают `profiles.data_lang` (`languageRule()` в `lib/ai/context.ts`): `en` — только английский, русские поля сервер обнуляет; `ru` и `ru_en` — оба языка одним запросом.
- Ответы только структурированным JSON (`responseMimeType: application/json` + `responseSchema`).
- Голос: записываем на клиенте через `MediaRecorder` (`lib/audio/`), до 20 секунд, и отправляем аудио в Gemini вместе с задачей (Gemini сам распознаёт речь на русском и английском). Safari пишет `audio/mp4`, Chrome `audio/webm` (WebM нет в списке форматов Gemini), поэтому запись всегда перекодируется на клиенте в **WAV 16 кГц моно** через Web Audio. Текстовое поле всегда доступно как альтернатива голосу.
- Маршруты с файлами принимают `multipart/form-data`: `audio` (WAV до 1,5 МБ), `image` (JPEG до 2 МБ), `text` (до 500 символов), `meta` (JSON). Категории и места для промпта сервер берёт из базы сам (`lib/ai/context.ts`), а не от клиента; любой id из ответа Gemini проверяется по этим спискам.
- В схемах ответа для Gemini «нет значения» = пустая строка или пустой массив (не `null`: поддержка null в JSON Schema у моделей разная); сервер превращает их в `null`.
- **Распознавание по фото** (`/api/ai/recognize`): фото + список категорий пользователя → `{ name_ru, name_en, description_ru, description_en, category_id | null, tags[] }`. Запускается автоматически после первого фото, если название пустое; заполняет только пустые поля; есть кнопка «Распознать заново».
- **Экран «Добавить вещь»** (`components/items/add-item.tsx`): до выбора фото только две одинаковые карточки — «Несколько вещей на одном фото» и «Одна вещь», в каждой «Снять фото» и «Из галереи». Фото из «Одной вещи» открывает обычную форму и сразу распознаётся (как первое фото в форме).
- **Несколько вещей на одном фото** (`/api/ai/recognize-multi`, `components/items/multi-add.tsx`): одно фото → до 30 предметов `{ name_*, description_*, category_id | null, tags[], box }`, `box` = `box_2d` Gemini `[ymin, xmin, ymax, xmax]` в 0–1000; 1 запрос = 1 единица лимита (вид `recognize`). Схема для модели **без ограничений длины и количества** (вложенные лимиты на списке в 30 объектов Gemini отклоняет: «too many states»), сервер сам обрезает строки, теги, число предметов и отбрасывает кривые/крошечные рамки. Клиент вырезает предметы из полного разрешения с отступом ~6% (`openPhoto().crop()` в `lib/photos/process.ts`), сжимает как обычные фото. Экран проверки: галочки, название по режиму языков, категория, одно место на все («Я здесь», LocationPicker или голос `/api/ai/place` в `mode: "move"`). Сохранение — server action `createItemsBatch`: вырезки клиент грузит в папки своих вещей, общий снимок один раз в папку первой вещи, сервер копирует его (`storage.copy`, пара файлов) в папки остальных; главное фото — вырезка, второе — общий снимок. Каждая вещь владеет своими файлами, поэтому удаление работает как обычно. Ноль или один предмет → «Добавить как обычно»: обычная форма получает фото и распознанные поля (`ItemForm seed`) без нового запроса к ИИ.
- **Защита от дублей** (без ИИ, `app/(app)/items/duplicate-actions.ts`):
  - *тот же снимок:* клиент считает SHA-256 исходного файла (`lib/photos/hash.ts`), он сохраняется в `item_photos.source_hash` (у фото одиночной вещи и у всех копий общего снимка; у вырезок null). `findPhotoUses(hashes)` до запроса к ИИ: в «Нескольких вещах» вместо поиска показывается «Этот снимок уже добавлен: N вещей» (`PhotoUsedNotice`) с «Всё равно распознать» / «Отмена»; в обычной форме новой вещи то же предупреждение, автораспознавание ждёт «Всё равно распознать». Заново снятая фотография — другой файл, её ловит вторая проверка;
  - *похожие вещи:* `findSimilarItems` → SQL `similar_items(p_names_ru, p_names_en, p_location_id, p_min)` (security invoker, pg_trgm по названиям, `ё`→`е`, вещи в выбранном месте и вложенных первыми), порог 0,5 подобран на реальных повторах. Карточки с совпадением получают строку «Похоже, уже есть: «…»» и снятую галочку, пока пользователь сам её не трогал; проверка повторяется при смене места.
- **Голос в текстовых полях** (`/api/ai/transcribe`, `components/dictation-field.tsx`): микрофон у названий (все `NameFields`: вещи, места, категории) и описаний вещи. WAV + `{ lang, kind: name | description }` → `{ text }` (вид лимита `transcribe`, 1 запись = 1 единица). Текст **всегда на языке поля** (сказанное на другом языке переводится), только исправление явных ошибок распознавания и пунктуация, без пересказа; пустой ответ — «Не расслышал». Результат — карточка под полем: «Вставить» (пустое поле) или «Заменить» / «Дописать в конец», «Отмена»; без нажатия поле не меняется. В `ru_en`, если во втором языке уже есть текст, после правки предлагается «Обновить перевод (EN/RU)» через `/api/ai/translate`; в `ru` английский переводится в фоне после сохранения, как обычно. Без сети кнопка неактивна; запрет микрофона — сообщение `micDenied` под полем.
- **Место по голосу** (`/api/ai/place`): аудио или текст + список мест пользователя в виде `{id, path_ru, path_en}` → `{ match: location_id | null, create: { parent_id, names: [{name_ru, name_en}, ...] } | null, ambiguous: location_id[] }`. Если места нет, приложение показывает «Создать "Верхняя полка" внутри "Дача → Спальня → Шкаф"?» и создаёт только после подтверждения. Если подходит несколько мест (спальня есть в двух домах), просим выбрать. Работает в форме вещи (`mode: "form"`) и в «Переместить» на карточке (`mode: "move"`). Текущее «Я здесь» передаётся как подсказка для «сюда». В форме ответ дополнительно содержит `item`: предложенные правки названия, описания (полный новый текст на обоих языках) и `tags_add` из той же фразы («это старая дрель отца, не работает…»); форма показывает их карточкой «Принять / Отклонить» и сама ничего не меняет. Цепочка новых мест создаётся server action `createLocationChain` только после подтверждения.
- **Поиск голосом** (`/api/ai/search`): аудио или текст → Gemini возвращает `{ transcript, terms: string[] (синонимы на обоих языках), category_id | null, location_id | null }` → поиск по базе через `search_text` и фильтры. Всю базу в Gemini НЕ отправляем (только названия категорий и пути мест).
- **Поиск двухступенчатый** (`/search`): обычный текстовый поиск без ИИ срабатывает сразу при вводе (`?q=`), умный — по кнопке «Спросить ИИ» или микрофону (`?ai=1&q=<transcript>&t=<terms>&loc=&cat=`). Оба идут через SQL-функцию `search_items_v2(p_terms, p_location_id, p_category_id, p_limit)` (security invoker, по `search_text_v2`): нормализация `ё`→`е`, для слов от 5 букв совпадение без последней буквы (окончания; кроме чисел), слово-ISBN с дефисами или пробелами ищется по цифрам, сортировка по числу совпавших слов, затем по дате.
- **Книги** (v1.8.0):
  - *Распознавание:* `recognize` и `recognize-multi` возвращают `book: { author, year, isbn } | null` (поля модели `is_book`, `book_*`, правила в `lib/ai/books.ts`). Название книги — как напечатано, без перевода, в оба поля названия. Книга идёт в категорию пользователя «Книги»/«Books» (поиск по названию, `isBooksCategoryName`); если такой нет — карточка «Создать «Книги»?» (`BooksCategoryCard`, обычный `createCategory`). Если Gemini прочитал ISBN, сервер дозаполняет автора и год из каталогов (не ИИ). Полка с корешками — через «Несколько вещей», каждая книга — карточка со строкой «Автор · год».
  - *Штрихкод:* первое фото новой вещи сначала проверяется на EAN-13 978/979 на телефоне (`lib/books/barcode.ts`: родной `BarcodeDetector`, иначе лениво `barcode-detector` с zxing-wasm). Wasm раздаёт само приложение: `scripts/copy-zxing.mjs` копирует его в `public/zxing/` перед `dev`/`build` (папка не в git), он исключён из предкеша service worker (`globIgnores`) и из `proxy.ts`. Книга найдена по ISBN → форма заполняется, Gemini не вызывается (кнопка «Распознать по фото» остаётся); не найдена → сохраняется только ISBN и идёт обычное распознавание.
  - *Каталоги:* `/api/books/isbn` (`lib/books/lookup.ts`, сессия + `is_active()`, 30 запросов в минуту на пользователя в памяти экземпляра, кеш ответов на сутки): Open Library, недостающие поля — Google Books; для русскоязычных групп ISBN (978-5, 978-985, 978-966, 978-601) наоборот: сначала Google Books, Open Library дозаполняет (`catalogueOrder`: Open Library знает их плохо — неверные авторы, транслит). `GOOGLE_BOOKS_API_KEY` необязателен; без ключа часто 429. Наружу уходит только ISBN. Квота ИИ не тратится. Название — в пустые поля названия видимых языков, описание — в поле языка книги, если он показывается.
  - *Показ:* «Автор · год» под названием в карточке вещи, галерее и таблице; ISBN в карточке. Блок «Книга» в форме виден, если есть данные книги, выбрана категория «Книги» или нажато «Это книга: автор, год, ISBN»; рядом поиск по ISBN.
- **Массовые изменения** (v1.9.0, `components/items/selection.tsx`, `bulk-bar.tsx`, `app/(app)/items/bulk-actions.ts`):
  - *Выбор:* в «Вещах» (галерея и таблица) и в результатах «Поиска» — кнопка «Выбрать» или долгое нажатие (~0,5 с, `SelectableLink`: системное меню ссылки подавлено, клик после долгого нажатия вещь не открывает). Шапка выбора закреплена под шапкой приложения: «Выбрано: N», «Выбрать все найденные», крестик. «Все найденные» в «Вещах» — `selectAllItemIds(filters)` на сервере (все вещи фильтров, не только загруженные), не больше 500 с сообщением «Выбраны первые 500 из N»; в «Поиске» — все результаты.
  - *Панель* (`BulkBar`, `fixed` над нижним меню): «Категория» (список + «Создать», название в языке показа), «Переместить» (`LocationPicker`, первым «Сюда, «Я здесь»», голос `PlaceAssistant mode="move"`; «Я здесь» не меняется), «По категориям» (ИИ), «Удалить» (подтверждение, фото парами из Storage).
  - *Сервер:* одна server action на операцию: `getUser` + `is_active()`, zod (до 500 uuid), запросы `.eq("user_id")` поверх RLS, id пачками по 100 (фильтры PostgREST идут в URL). Ответ изменений содержит прежние значения каждой вещи (`previous`).
  - *Отмена:* 10 секунд плашка «Изменено N · Отменить» (`UndoToast`, модульный стор: список после изменения пересоздаётся) → `bulkRestore` возвращает каждой вещи её значение. Удаление не отменяется; созданные категории остаются.
  - *Список после изменения:* `useBulkVersion()` — ключ списка, `forgetLoadedItems()` сбрасывает подгруженные страницы.
  - *«По категориям»* (`/api/ai/categorize`, вид квоты `categorize`): клиент шлёт только id (до 50 = 1 запрос), тексты сервер читает сам под RLS (названия, описания, теги, автор/год книги), без фото. Ответ: своя категория или новая (названия по режиму языков; совпадающая по названию с существующей — существующая) + уверенность. До запуска «Это займёт N запросов, осталось M» (`aiRequestsLeft`); при лимите посреди — показывается разобранное. Экран проверки: «было → станет», без неизменённых, неуверенные (< 0,6) без галочки, блок «Создать новые категории?»; применяется только по «Применить» (`bulkApplyCategories`).
- Результат ИИ только предзаполняет форму или предлагает действие. Сохраняет всегда пользователь.

## Правила работы

- Mobile-first: экран ~375px, кнопки не меньше 44px, нижняя навигация, большая кнопка «добавить» с камерой. Десктоп не должен ломаться.
- Весь текст интерфейса только через словари `next-intl`, никаких строк прямо в компонентах.
- Перед загрузкой фото сжимаем на клиенте (`lib/photos/process.ts`): длинная сторона до 1600px, JPEG ~80%, плюс миниатюра 480px, JPEG ~75%. Поворот по EXIF делает браузер при декодировании; пересжатие через canvas убирает все метаданные (в том числе GPS). HEIC: если браузер сам не декодирует, лениво грузится `heic-to` (WebAssembly, ~3 МБ).
- Миниатюра лежит рядом с основным файлом: `{uuid}.jpg` и `{uuid}.thumb.jpg`; в `item_photos` хранится только основной путь, путь миниатюры выводится (`lib/photos/paths.ts`). **Удаляем всегда пару файлов** (`photoFiles()`), при удалении фото и вещи.
- Загрузка: клиент сам генерирует `item_id`, грузит файлы прямо в Storage (RLS по папке), затем server action сохраняет вещь и `item_photos`; сервер принимает только пути `{свой user_id}/{этот item_id}/{uuid}.jpg` и при ошибке удаляет загруженные файлы. Фото в server action не передаём (лимит тела 1 МБ). Не больше 10 фото на вещь, ровно одно главное.
- Фото показываем через signed URLs (1 час), в списках — миниатюры; `next/image` для них не используем. Подписанные ссылки сервер переиспользует (кеш по пути в `lib/items/data.ts`, пока до истечения больше 10 минут), иначе каждая новая подпись — новый URL, и браузер заново качает все миниатюры.
- **Список «Вещи»**: сервер отдаёт первую страницу (`ITEMS_PAGE_SIZE` = 48), следующие подгружает клиент при прокрутке (`useMoreItems`, server action `loadMoreItems`, `listItems({ offset })`) и дописывает к уже показанным; подгруженное хранится на время вкладки по фильтру, поэтому «назад» восстанавливает всю длину списка и позицию. Кнопка «Показать ещё» — запасной вариант. Карточки вне экрана не отрисовываются (`content-visibility: auto`). `app/(app)/loading.tsx` — каркас, который виден сразу при переходе.
- **Регион**: функции Vercel закреплены в `iad1` (`vercel.json` → `regions`), рядом с Supabase (`us-east-1`). При смене региона Supabase менять и его.
- **PWA:** манифест `app/manifest.ts`, иконки в `public/icons/` (192/512 + maskable), `app/apple-icon.png`, `app/icon.svg`. Service worker — `lib/pwa/sw.ts` (Serwist, `@serwist/turbopack`), отдаётся маршрутом `/serwist/sw.js`, регистрируется только в production (`components/pwa-provider.tsx`, `cacheOnNavigation` и `reloadOnOnline` выключены). **Кешируем только статику** (`/_next/static`, иконки, шрифты). Страницы, RSC, `/api`, Supabase и фото НЕ кешируем: данные персональные, на общем телефоне кеш показал бы чужие данные после выхода. Без сети любая страница показывает предкешированный `/offline`; в приложении плашка «Нет сети» и кнопки сохранения/ИИ недоступны (`useOffline`). `lib/pwa/sw.ts` исключён из основного tsconfig (у него свой, с lib WebWorker).
- `/serwist`, `/offline` и `/help` открыты в `proxy.ts` без сессии.
- **Кнопка «Назад»** (`components/back-button.tsx`, `lib/nav-history.ts`): стрелка в шапке на внутренних экранах (вещь, правка, место, `/admin` и его разделы; на пяти вкладках нет), своя ссылка в шапке `/help`. Каждая запись истории, созданная приложением, получает номер `history.state.__inventoryIdx` (обёртка над `pushState`/`replaceState`, номер ставится заново при каждом replace — Next.js пересобирает state). Номер > 0 → `router.back()` (фильтры в адресе, вид в localStorage, прокрутку восстанавливает Next), иначе — родитель (`useParentPath`: вещь → `/`, правка → вещь, место → родительское место или `/locations`, `/admin/users` и `/admin/plans` → `/admin`, `/admin` → `/settings`, `/help` → `/settings` или `/login`). Состояния внутри одного адреса берут стрелку через `setBackOverride` (форма «Одна вещь» → две карточки, «Несколько вещей» → как «Отмена»). Новые внутренние экраны добавлять в `useParentPath`.
- **iPhone:** у `html`/`body` `overscroll-behavior-y: none` (без «резиновой» прокрутки страницы, иначе закреплённые панели уезжают); нижняя панель `fixed` + `transform-gpu`, шапка `sticky`, отступы `env(safe-area-inset-*)`; `100vh` не используем (для высоты — `dvh`). У родителей закреплённых панелей не должно быть `transform`/`filter`/`contain`.
- **Сессия:** `proxy.ts` проверяет её только по подписи токена (`getClaims`, ES256, без сети), страницы — через сервер Auth (`getUser`). Отозванная сессия (выход на другом устройстве со scope global, смена пароля) до часа выглядит живой для proxy, поэтому `requireUser()` при отсутствии пользователя ведёт на `/auth/signout` (очищает cookie `sb-*` этого устройства → `/login`), а не прямо на `/login`: иначе бесконечный цикл `/` ↔ `/login`. «Выйти» — `signOut({ scope: "local" })`, только это устройство.
- **Инструкция** `/help`: короткие разделы с иконками (тексты в `help` словарей, списки через `t.raw`), доступна до регистрации. Ссылки: экран входа, Настройки, последний шаг онбординга. Новые функции добавляем и в неё.
- **Заголовки безопасности** задаются в `next.config.ts` (`nosniff`, `X-Frame-Options`, CSP `frame-ancestors/base-uri/object-src`, `Referrer-Policy`, `Permissions-Policy` с камерой и микрофоном только для себя, HSTS).
- **Онбординг** при первом входе (нет мест, нет вещей, нет `user_metadata.onboarded`): три шага, можно пропустить; по завершении `updateUser({ data: { onboarded: true } })`.
- **Удаление аккаунта** (Настройки): пароль + слово «УДАЛИТЬ»/«DELETE»; server action заново проверяет пароль, удаляет все файлы пользователя через Storage API (прямое удаление из `storage.objects` Supabase запрещает), затем RPC `delete_my_account()` (SECURITY DEFINER, удаляет только `auth.uid()`, всё остальное каскадом).
- Отчёт о проверке безопасности: `docs/security-review.md`. При новых таблицах и маршрутах повторяем те же проверки.
- Изменения схемы только новой миграцией, старые миграции не редактируем.
- Работаем маленькими шагами: короткий план → код → проверка (`npm run build`, `npm run lint`, ручная проверка в мобильном размере).
- После каждого законченного этапа коммит с понятным сообщением и push **ветки задачи** (не main, см. «Релизы»).
- Если требование неясно или выбор меняет архитектуру, сначала спроси.

## Релизы (обязательно в каждой сессии)

У приложения живые пользователи, а база Supabase одна на всё: Preview, локальная разработка и production работают с одними и теми же данными.

**Ветки и деплой**
- Каждая задача в своей ветке `feature/<коротко>` от свежего main. Коммиты и push только в неё; push создаёт Vercel Preview.
- После push присылать пользователю адрес Preview ветки: `https://ed-inventory-git-<ветка, / → ->-guzmans.vercel.app` (например `feature/foo` → `ed-inventory-git-feature-foo-guzmans.vercel.app`).
- **В main ничего не сливать и не пушить без явной команды пользователя «выкатывай».** Одобрение одной выкатки не распространяется на следующие.
- Production: `https://ed-inventory.vercel.app`. Supabase Auth Redirect URLs: production, `https://ed-inventory-*-guzmans.vercel.app/**`, `http://localhost:3000/**`.
- Preview закрыт Vercel Deployment Protection (вход в Vercel или ссылка Share); защиту не отключаем. `SUPABASE_SERVICE_ROLE_KEY` в окружении Preview нет: админское «Удалить пользователя» на Preview не работает, это ожидаемо. Cron работает только на production.

**Миграции при одной базе**
- До выкатки разрешены только изменения, не ломающие текущую рабочую версию: новые таблицы (с RLS по правилам выше), новые колонки с `default` или nullable, новые функции и представления, индексы, политики, которые ничего не отнимают.
- Ломающие (удалить или переименовать колонку/таблицу, `not null`, новый `check`, ужесточить RLS, изменить поведение существующей функции, триггера или представления) — **отложенные**: лежат в `supabase/deferred/` (туда `db push` не смотрит), к каждой заранее пишется обратный `*.down.sql`. При выкатке переносятся в `supabase/migrations/` с новым временем в имени и применяются отдельным шагом **после** деплоя нового кода. Новый код должен работать и до, и после отложенной миграции.
- Перед каждым `db push` явно написать: «Миграция X: безопасна для текущей версии / ломающая, потому что …» и дождаться «да» пользователя.

**Тестирование**
- Preview проверяем под отдельным тестовым аккаунтом (email с `+test`, активирован в `/admin`), не под аккаунтом владельца и не под пользователями. Его логин и пароль только в `.env.local` (`TEST_USER_EMAIL`, `TEST_USER_PASSWORD`), не в git. Админские функции проверяются под админом, но действия только над тестовыми аккаунтами.

**Выкатка по команде «выкатывай»**
1. В ветке: `npm run lint`, `npm run build`; Preview проверен.
2. Запись в `CHANGELOG.md` и `version` в `package.json` (+ `package-lock.json`), semver: исправления → Z, новые функции → Y, ломающие для пользователя изменения → X.
3. `git checkout main && git pull && git merge --no-ff feature/…`, тег `vX.Y.Z` (annotated), `git push origin main --follow-tags`.
4. Дождаться деплоя production (Ready) и проверить рабочий сайт: `/login`, `/help`, `/offline` отвечают 200, вход тестовым аккаунтом, главные экраны и новая функция.
5. Отложенные миграции: дамп затронутых данных (`npx supabase db dump --data-only` в scratchpad, не в git: там личные данные; у Supabase Free нет доступных бэкапов) → «да» пользователя → `db push --remote` → `npm run db:types` → снова проверка сайта.
6. Короткий отчёт: версия, что вошло, результаты проверок. Ветку задачи после выкатки можно удалить.

**Откат**
- Код: Vercel → Deployments → Instant Rollback к предыдущему production (без пересборки; на Hobby только на один деплой назад). После отката Vercel не выкатывает новые пуши в main сам: нужно Promote нужного деплоя или Undo Rollback.
- Безопасные миграции не откатываем: старый код их не замечает.
- Если уже применена ломающая миграция: сначала её `*.down.sql` (с «да» пользователя), затем Instant Rollback кода; удалённые данные — из дампа шага 5.

## Команды

```
npm run dev        # локальный запуск
npm run build      # проверка сборки
npm run lint
npx supabase db push --remote   # применить миграции к проекту Supabase (CLI не ставим, только npx; без --remote CLI 3.x идёт в локальную БД)
npm run db:types               # перегенерировать lib/supabase/database.types.ts после миграции
```
